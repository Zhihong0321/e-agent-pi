为什么

AI 每三个月就有新突破，为什么稳定、高效的 AI 数字工人迟迟没有出现？

我们的答案：化繁为简 · 化简为元

AI 进步神速，几乎每三个月就有颠覆性的新能力。但稳定、高效的数字工人迟迟没有出现。经过内部多年打磨和使用，我们定制出一个“化繁为简”的 AI Agent 框架：核心是 micro-agent。接下来先讲“化繁为简”，再讲“化简为元”。

E · Document Intelligence · 化繁为简

把工作拆成多个 workflow，每个 micro-agent 只负责一个小类别或一条特定流程。类似单细胞：处理更严谨，也更容易被 Harness 规范。这里是 Document Intelligence 里的 6 个 agent。设计原则：按“权限”拆分，而不是按动词拆分——创建和修改单据共享同一份知识，所以是同一个 agent；改公司规则是另一种权限，所以是另一个 agent。

化繁为简

更好管：Harness 加 Checker

HARNESS

把边界写死

  • 只能通过指定工具工作：没有文件、没有 Shell、没有 SQL
  • 只看得到自己的工具，借不到别人的；主机再校验一次
  • 不持有数据库密码，所有操作由主机代为执行

CHECKER AI

对照输入与结果

  • 开单、收款、作废、发布等不可逆操作，先核对用户是否真的这样要求
  • 回复后核对单号、金额、状态是否与数据库一致
  • 不达标就退回原 Agent 重做，最多 2 次

评测环境已验证 · 接入线上对话为下一步

E · Document Intelligence · 化繁为简

Harness：agent 运行在 assistant 权限下，没有文件、Shell、SQL，唯一能力是 MCP 工具，且每个 agent 只看到自己的工具；主机会再校验一次，每个 agent 的令牌不能冒充别的 agent。Checker：一个独立的模型（与工作模型不同家族），只在不可逆写入前和回复后介入；不达标退回原 agent，最多重试 2 次，之后带着“Checker 未能确认”的提示发出。判断出错时放行，不阻塞工作。诚实说明：目前 Checker 在评测环境中运行并验证，尚未接入线上聊天。

软化后的说法：不是“Agent 随意改 schema”，而是“标准结构 + 按公司调整的设定”。自定义字段存放在每条记录的 custom（JSONB）里并在每次保存时校验；开单规则、编号、税码都是数据。字段类型设定后不能更改。需要真正的索引列或类型列的重度定制，未来会走“生成迁移文件、由人审核执行”的提案流程，绝不由 agent 直接改表。

E · Document Intelligence · 数据库守底线

这是原有介绍里没有提到、但已经实现的最强卖点。全部由数据库强制执行：delete/truncate 触发器（连表的拥有者角色也被拦住），每张表的行级安全策略 tenant_id = 当前公司，issued 单据的 guard 触发器，编号在开单事务里用 SELECT ... FOR UPDATE 分配，audit 触发器记录 actor、agent 与前后值，且 di_app 角色不能改或删审计日志。代理还有另一层：工具不广播 + 主机拒绝 + 每个 agent 的 HMAC 令牌不可重放。

数据库守底线 · 细节

E · Document Intelligence · 数据库守底线

客户去重的打分：SSM 号或 TIN 100，邮箱 90，电话 75，名称 80，同公司邮箱域名 60，名称相似 55 或 30，已是联系人再加 15。90 分以上视为已存在，40–89 为可能，需要用户确认。压力测试里有一份工作报告藏了一句指令，Form Clerk 把它当作不可信数据，没有照做。MyInvois：TIN、MSIC、SST 号、e-invoice 字段已预留，缺 TIN 只是警告；LHDN API 对接尚未做。
