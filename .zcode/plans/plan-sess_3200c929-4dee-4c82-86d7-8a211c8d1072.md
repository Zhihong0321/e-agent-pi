## Goal
Unify internal Company Persons and system Users into one person-management experience: one agent/tool/API flow for profile, contact, department, and optional system login credentials. Keep external customer contacts separate and preserve existing records.

## Design
Use `users` as the canonical system identity for people who have (or may later receive) access, while retaining `di.company_member` as a tenant-scoped compatibility/profile record during migration. Add a nullable link from the company-member record to `users`, and expose a joined person DTO through one management API/tool. This avoids breaking existing document-intelligence tenant isolation, customer contacts, activity attribution, or current session security while eliminating the two user-facing management concepts.

Optional login is explicit: a person can exist without credentials; login is enabled only when a valid username and password are supplied. Passwords are always stored through the existing hashing path, never returned by list/read APIs, and changing password, disabling access, or changing role invalidates sessions.

## Implementation steps

1. **Schema and migration**
   - Extend the existing `users` schema additively with person profile fields needed by Company Person (email, phone, department, position/title, location, notes) and an explicit login-enabled/credential state compatible with current users.
   - Add a nullable `user_id` reference on `di.company_member` (with an index and safe foreign-key behavior). Keep the existing member row and tenant scoping so old records are not lost.
   - Make migration idempotent in the existing startup/schema paths and add migration tests for fresh and already-populated databases.
   - Backfill/link existing company members to users by normalized email where there is exactly one safe match; leave unmatched members intact and login-disabled. Do not merge external `di.contact` customer records.

2. **Unified server/domain service**
   - Add a shared person-management service (near `server/users.mjs` or a dedicated module) that validates and normalizes profile fields, resolves a person by user/member id, and returns a joined person view with `has_login`/`active` but never password hashes.
   - Implement list/create/update operations transactionally. A create/update from the person flow must update the profile/member link and, when requested, create or update login credentials in the same transaction.
   - Preserve existing protections: current-admin capability for management, username validation, last-active-admin protection, duplicate-email/member checks, session invalidation on credential/access changes, and tenant isolation.
   - Keep the old `list_users/create_user/update_user` behavior as a compatibility wrapper over the new service, so existing callers and login continue to work while returning the richer person fields.

3. **Agent/tool consolidation**
   - Add one unified tool contract (for example `list_people`, `create_person`, `update_person`) to the user-management/orchestrator tool surface, with fields for name/display name, position, department, email, phone, location, username, password, role, tier, and active/login access.
   - Update the Company Person/document-intelligence tool surface so its internal-member operations call the unified service or its adapter rather than creating a separate identity path. Preserve the separate customer-contact tools.
   - Update the relevant agent prompts/descriptions so the agent treats “person” and “user” as the same internal entity, asks whether login access is wanted, and never exposes passwords or capability tokens.
   - Retain old tool names as aliases during the transition where tests or clients depend on them.

4. **HTTP/API and frontend**
   - Extend the existing demo action/API and authenticated user-management route with unified person actions, using the current auth/session middleware rather than a new credential mechanism.
   - Replace the PeoplePanel’s “Save company person” flow with a unified person form: profile/contact/department fields plus an optional “Enable system login” section (username, password, role/access status). Show login status, never a password.
   - Add edit support and clear states for contact-only vs login-enabled people; keep vCard import and the existing work-email/phone validation.
   - Add a people/users admin view in the existing settings/admin area or reuse the existing user-management surface, so there is one list and one edit action instead of separate person and user screens.

5. **Tests and verification**
   - Add/extend unit tests for schema migration, email matching/backfill, contact-only creation, login-enabled creation, password hashing/non-disclosure, role/last-admin rules, session invalidation, duplicate detection, and tenant isolation.
   - Add API/agent-tool tests proving both the old user actions and new person actions operate on the same record and that customer contacts remain separate.
   - Run the existing server/document-intelligence/frontend test, typecheck, and build suites; verify the login flow with a created login-enabled person and verify a contact-only person cannot authenticate.
