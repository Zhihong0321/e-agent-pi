## Goal
Add a first-class **Media AI** specialist that collects and manages a company Media Kit, persists asset metadata safely, and provides a polished company-facing showcase/share experience for logos, event photos, news, certifications, qualifications, and awards.

Because no clarification selection was returned, use this conservative MVP default: authenticated company management plus a controlled shareable showcase link, surfaced as a dedicated `/media-kit` page. Preserve all existing working-tree changes; do not reset, stash, or overwrite unrelated files.

## Architecture

1. **Reuse immutable binary storage**
   - Keep using the existing `publishFile()` / `/files/<id>/<filename>` mechanism for asset bytes and immutable versions.
   - Do not use legacy `/api/files/raw` URLs as durable Media Kit references.
   - Store a normalized file reference (`file_id`, filename, bytes, MIME, URL/link) in Media Kit metadata.

2. **Add a tenant-scoped Media Kit metadata model**
   - Add a new SQL migration following the existing `di.current_tenant()`, RLS, audit, soft-delete, and migration conventions.
   - Use one flexible `media_kit_asset` table rather than six disconnected tables. Include:
     - asset id, tenant id, category (`logo`, `event_photo`, `news`, `certification`, `qualification`, `award`);
     - title, description/caption, alt text, language, event/news/issue date;
     - issuer/source, credential or external URL fields where applicable;
     - published/draft/archive visibility state and display order;
     - immutable shared-file id/name/MIME/bytes/link metadata;
     - structured `metadata jsonb` for category-specific fields;
     - created/updated/soft-deleted audit fields and an optimistic revision/version.
   - Add indexes for tenant/category/status/order/date and any uniqueness needed for duplicate file references.

3. **Implement a dedicated Media AI host/MCP package**
   - Add `server/media-ai/` patterned after `server/company-research/`, but keep the first version synchronous and simple rather than introducing a research-style background queue.
   - Provide narrowly scoped authenticated host actions/tools for:
     - list/search/filter assets;
     - ingest an uploaded/workspace file by publishing it through the existing share path;
     - create/update metadata;
     - archive/restore assets;
     - generate a kit summary/manifest and return structured asset references.
   - Enforce company context on the host side; never allow the agent to select a tenant or publish arbitrary paths outside its workspace.
   - Validate MIME, filename, size, required category fields, dates, URLs, and metadata. Reject traversal, symlink escapes, empty files, and malformed file references.
   - Deduplicate by immutable published file id/content while allowing multiple intentional metadata records when needed.
   - Return `shared_files` in the existing structured format so files propagate through agent turns, orchestrator tasks, and the UI.

4. **Register the Media AI specialist and make orchestration explicit**
   - Add a stable Media AI identity/role constant in `server/paths.mjs` and a role file such as `agent/roles/media-ai.md`.
   - Seed a protected catalog agent with a clear headline/description and `assistant` tool profile, attach only the Media AI MCP, create its workspace, and use a scoped host token/environment branch.
   - Register/upsert the MCP during server boot, following the Company Deep Research registration pattern.
   - Extend the Orchestrator role guidance so it recognizes Media Kit work and routes collection/normalization/publishing tasks to the Media AI specialist with explicit acceptance criteria (valid category metadata, company ownership, approved visibility, and shared-file references).
   - Do not hard-code specialist discovery in the orchestrator: rely on the existing roster/list-specialists path so the new agent appears automatically.

5. **Expose authenticated management and controlled sharing APIs**
   - Add company-scoped JSON endpoints following the existing demo/company-profile auth and `no-store` response conventions:
     - list/get assets with category/status/search filters;
     - upload/publish an asset and create metadata;
     - update metadata/order/status;
     - soft archive/restore;
     - build a shareable kit manifest.
   - Add a share-token model/route for the controlled showcase link. Store only a hash of the token, scope it to the company/kit, support expiration/revocation, and expose only assets marked shareable/published.
   - Keep ordinary owner/admin management separate from public/link-view access. Do not weaken the existing authenticated `/files/` download route; the share view should resolve allowed asset references through a guarded manifest/file-serving path.
   - Ensure company switching and token scope cannot leak another tenant’s metadata or files.

6. **Build the dedicated Media Kit showcase UI**
   - Add a `/media-kit` route in `src/main.tsx` and a focused page/component rather than coupling the first version tightly to the large demo workspace.
   - Reuse the existing demo visual language and primitives: white bordered panels, green/mint tokens, responsive cards, image lightbox, file links, status chips, and mobile breakpoints.
   - Include:
     - branded company hero with logo and profile identity;
     - category tabs/filter/search for logos, events, news, certifications, qualifications, awards;
     - responsive asset gallery with image previews/lightbox and PDF/document download cards;
     - metadata-rich detail cards (caption, date, issuer, credential, source/credit);
     - management actions for upload, edit, archive, reorder, and publish/share;
     - share-link creation/copy/revoke and a read-only share view that hides drafts/private assets;
     - empty/loading/error states and clear validation feedback.
   - Use the existing credentialed fetch helper patterns and network-only behavior for live API data. Keep global CSS changes narrowly scoped to Media Kit classes.

7. **Testing and verification**
   - Add database/domain tests for migration idempotence, RLS/tenant isolation, soft deletion, revisions, category validation, and share-token hashing/expiry/revocation.
   - Add Media AI host/MCP tests for authorization, path safety, publishing, deduplication, structured metadata, and `shared_files` output.
   - Add orchestrator/catalog tests proving the Media AI appears in the specialist roster, cannot be self-dispatched/deleted if protected, and can complete a media-kit plan with acceptance criteria.
   - Add API tests for CRUD, upload failures, company switching, private/public filtering, and share-link access.
   - Add frontend build/lint checks and a browser smoke test for `/media-kit`: login, upload/list state, category filtering, image preview, publish/share, and read-only share rendering.
   - Run only focused tests first, then the frontend build/lint. Report any pre-existing failures separately from feature failures.
