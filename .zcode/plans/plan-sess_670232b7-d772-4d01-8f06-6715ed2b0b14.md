## Goal
Build a company-scoped calendar page that presents date-bearing business information in one minimalist calendar, initially covering quotation expiry, invoice payment due dates, and reminders/attention items. Add a read-only calendar AI/data layer that can discover and normalize new date-bearing fields as schemas evolve without allowing the model to issue arbitrary SQL or mutate company data.

## Architecture

1. **Trusted read layer (deterministic, tenant-scoped)**
   - Add a calendar data module under `document_inteligence/core/` that runs parameterized queries inside the existing `withContext()` transaction and inherits PostgreSQL RLS/company isolation.
   - Read the current canonical sources: documents (`valid_until`, `due_date`, `issue_date`, status/type), payment receipts (`received_on`), form deadlines/submissions where applicable, company timezone, and metadata/custom-field definitions.
   - Add bounded date-range inputs, source filters, pagination/limits, and explicit all-day/date-only handling. Do not expose raw SQL construction to an LLM.
   - Extend or add a read-only DI tool registration in `document_inteligence/core/tools.mjs` and the DI MCP server so the calendar agent receives structured source rows plus schema metadata/provenance.

2. **Calendar AI/normalization layer (read-only)**
   - Add a pure normalizer/contract module, likely `document_inteligence/core/calendar.mjs`, with a versioned event shape such as:
     - deterministic event id
     - title and event kind (`quotation_expiry`, `payment_due`, `reminder`, etc.)
     - start/end or date-only value
     - `allDay`, company timezone
     - status/severity and display color category
     - customer/document/payment references
     - source table/record/field provenance
     - confidence and warnings/needs-review flags
   - Use schema introspection (`entity_def`, `field_def`, `custom` JSON, form schemas) to discover date-typed custom fields and candidate date keys rather than hard-coding only today’s invoice schema.
   - Keep deterministic mappings for known business semantics (quotation `valid_until`, invoice `due_date`, form closing date) and use the AI only to classify/label unknown candidate fields. Unknown or ambiguous values must be returned as `needs_review`, never silently guessed.
   - Validate ISO dates, IANA timezone identifiers, event identity/deduplication, and end-after-start constraints. Preserve source values and warnings so the UI can explain why an event exists.
   - Keep this capability strictly read-only: no insert/update/delete, no automatic status changes, and no direct database credentials in the model process.

3. **Agent/MCP registration and orchestration**
   - Add a dedicated calendar MCP/server registration following the existing idempotent DI/Sales MCP registration patterns.
   - Seed/attach a dedicated `assistant`-profile calendar agent with only the calendar read MCP; do not grant bash/edit/write tools.
   - If multi-step processing is needed, reuse the existing orchestrator/job policy: source read → normalization → independent checker → final event payload. Use existing dependency/checker gates and structured JSON outcomes; do not create a parallel job system.
   - Ensure the agent output is machine-readable JSON consumed by the page, with bounded output and provenance rather than generated HTML.

4. **Calendar page/template**
   - Add a new page route in the existing app workspace (prefer the current demo/company workspace shell and its navigation conventions rather than a separate application shell).
   - Add a minimal month view with:
     - month navigation and “today” control;
     - event density indicators in date cells;
     - selected-day agenda/list;
     - filters for event kind/status/severity;
     - clear visual distinction for expired quotations, upcoming payment due dates, and reminders;
     - compact event detail drawer/popover showing source document/customer, exact date, status, warning, and provenance;
     - loading, empty, error, and needs-review states;
     - responsive mobile layout that becomes an agenda-first view.
   - Keep the visual language aligned with `app/demo/page.tsx` and `app/demo/style.css`: existing rail/topbar, spacing, green/mint palette, focus states, and accessible controls. Avoid a heavy third-party calendar dependency unless the current project already has one; implement the small month grid from the normalized event contract.
   - Fetch only the selected visible range from a server API route, pass the authenticated company context server-side, and never accept an arbitrary tenant id from the browser.

5. **Server API and company scoping**
   - Add a company-authenticated calendar endpoint that accepts a bounded `from`, `to`, timezone/display options, and filters.
   - Resolve the host-held tenant/company context exactly as current DI APIs do; execute all reads through `withContext()`.
   - Return `{events, range, schemaVersion, generatedAt, warnings}` and expose source errors without leaking SQL, secrets, or cross-company records.
   - Cache only by tenant plus normalized range/schema version if profiling shows it is needed; preserve deterministic refresh behavior while schemas evolve.

## Tests and verification

- **Pure calendar tests:** known quotation/invoice/payment mappings, date-only/all-day behavior, timezone validation, unknown custom date fields, invalid dates, duplicate source records, conflicting/ambiguous fields, and warning/needs-review behavior.
- **DI/tool tests:** input validation, tenant context propagation, bounded ranges, read-only tool list, schema metadata handling, and no mutation paths.
- **MCP protocol tests:** tool names/schemas, structured output, empty ranges, malformed source rows, DB failure behavior, bearer/host boundary if applicable, and confirmation that no write tool is registered.
- **Orchestrator tests (if the DAG is enabled):** checker failure blocks formatting, invalid event dates are rejected, late/expired tasks do not replay, and no partial output is published.
- **API/page tests:** authenticated company scoping, range filtering, month navigation, event filters, selected-day details, loading/empty/error states, responsive agenda behavior, and accessibility labels/keyboard navigation.
- Run the existing test suite plus the new focused tests, start the app, and perform a black-box browser check of the calendar page. Refresh the graft graph after the code changes.

## Suggested implementation sequence

1. Add the normalized event contract and pure source mapping/validation tests.
2. Implement tenant-scoped calendar reads and schema/custom-field discovery.
3. Register the read-only tool/MCP and calendar assistant; wire checker/orchestrator only if needed by the runtime path.
4. Add the authenticated range API.
5. Build the calendar page/template and integrate navigation/styles.
6. Run focused/full tests, browser verification, and graph refresh; address failures before delivery.

## Explicit phase-1 boundary

The first version will display reminders/attention items that already exist in the database or are derived from date-bearing records. It will not invent appointments, send notifications, change invoice/quotation status, or create persistent reminders unless a later requirement adds an explicit write model and approval flow.
